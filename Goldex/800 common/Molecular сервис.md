Создай полностью автономный микросервис на **TypeScript**, совместимый с фреймворком **Moleculer**, предназначенный для обработки операций с **покупкой и продажей драгоценных металлов через вендинг-устройства** (слитки, монеты и т.п.).

## 1. Платформа и окружение

1. Основная целевая платформа — **Dyno** (типичный PaaS с контейнером / dyno-процессом):
    
    - Сервис должен корректно запускаться в контейнере.
        
    - Должен слушать порт из переменной окружения `PORT` (по умолчанию можно использовать `3000`).
        
    - На этом порту должен быть доступен лёгкий HTTP-сервер (см. раздел **4.5**), реализованный только на стандартном модуле `http`.
        
    - Должен корректно обрабатывать сигналы `SIGTERM` / `SIGINT` (graceful shutdown Moleculer-брокера).
        
2. Запасной вариант — **Node.js**:
    
    - Возможность локального запуска командой `npm run start` / `node dist/index.js` без привязки к конкретной PaaS.
        
    - Никаких платформенно-специфичных зависимостей, мешающих запуску в обычном Node.js окружении.
        
3. Версия Node.js — **>= 20**.
    

## 2. Функциональность (без жёсткой привязки к 2 actions)

1. Архитектура действий должна быть **расширяемой**:
    
    - Должно быть не меньше **двух примеров бизнес-операций** (например, `purchase` и `sell`),  
        но они не должны быть зашиты в систему как **единственно возможный** набор.
        
    - Добавление новых операций (например, `exchange`, `refund`, `diagnostics`) должно требовать **минимальных изменений** в инфраструктурном коде.
        
2. Валидация входных данных:
    
    - Использовать **`fastest-validator`** для всех публичных actions.
        
    - Все входные payload’ы валидируются схемами с понятными сообщениями об ошибках.
        
3. Взаимодействие с внешними системами:
    
    - Имитация получения курсов металлов и работы с платёжным шлюзом через моки или простые правила (фиксированный курс + маржа и т.п.).
        
    - Внешние интеграции должны быть абстрагированы через отдельные “адаптеры” / “клиенты”, чтобы можно было легко заменить моки на реальные API.
        

## 3. Архитектура сервиса

1. Использовать **Moleculer** в standalone-режиме:
    
    - Встроенный брокер Moleculer.
        
    - Локальный транспорт (никакого NATS/Kafka и т.п.).
        
    - При необходимости — `MemoryAdapter` для внутреннего состояния.
        
2. Структура проекта:
    
    - Отдельный файл конфигурации брокера `moleculer.config.ts`.
        
    - Основной сервис, например, `src/services/metal-vending.service.ts`.
        
    - Опционально: HTTP-шлюз через `moleculer-web` для REST API (бизнес-эндпоинты). Healthcheck при этом остаётся реализованным через отдельный лёгкий HTTP-сервер (см. 4.5), а не через `moleculer-web`.
        
3. HTTP API (если используется `moleculer-web`):
    
    - Единый префикс, например, `/api/metal`.
        
    - Маршруты, соответствующие actions (например, `POST /api/metal/operations/:type`).
        
    - Эндпоинты для **metrics** (см. раздел обсервобилити), если требуется.
        

## 4. Трейсабилити и обсервобилити

Добавь явные требования к **traceability** и **observability**, чтобы любой бизнес-запрос можно было проследить от входа до выхода:

1. **Корреляция запросов**:
    
    - Каждый входящий запрос (Moleculer action или HTTP-запрос через шлюз) получает уникальный `requestId` (или принимает его из заголовка/метаданных, если уже существует).
        
    - `requestId` / `correlationId` прокидывается:
        
        - во все лог-записи, связанные с обработкой запроса;
            
        - во все вызовы внешних адаптеров (курсы металлов, платежи и т.п.).
            
2. **Структурированные лог-записи**:
    
    - Логи — в структурированном формате (например, JSON) с полями:
        
        - `timestamp`
            
        - `level`
            
        - `service` / `action`
            
        - `requestId` / `correlationId`
            
        - краткое описание операции (тип, сумма, металл и т.п.)
            
        - `status` (`success` / `error`)
            
        - для ошибок — код и стек/сообщение.
            
    - Логирование:
        
        - входных параметров (без чувствительных данных);
            
        - результата операции;
            
        - ошибок и тайм-аутов внешних вызовов.
            
3. **Аудит-лог бизнес-операций**:
    
    - Для каждой завершённой операции создаётся запись в аудит-логе с полями:
        
        - `operationId`
            
        - `operationType` (purchase, sell, etc.)
            
        - `metalType`
            
        - `amount` (масса/сумма)
            
        - `rate` / `price`
            
        - `status` (completed, failed)
            
        - `createdAt`, `finishedAt`
            
        - `requestId`
            
    - Хранение аудит-лога:
        
        - в минимальном варианте — в памяти (`MemoryAdapter`) либо в простом хранилище (файл/JSON).
            
    - Интерфейс к аудит-логу должен позволять получить операцию по `operationId` / `requestId`.
        
4. **Метрики** (обсервобилити):
    
    - Счётчики по операциям:
        
        - количество операций по типу (`operationType`) и металлу (`metalType`);
            
        - количество ошибок по типу.
            
    - Простая метрика по времени обработки:
        
        - измерение latency (например, время выполнения action) и логирование/агрегация.
            
    - Желательно предусмотреть точку расширения для интеграции с **OpenTelemetry** (spanId/traceId, exporter), но не обязательно подключать полноценный стек.
        
5. **Лёгкий HTTP health endpoint (Node.js `http`)**:
    
    Реализуй отдельный минимальный HTTP-сервер на **Node.js** только на встроенном модуле `http` (без Express и других библиотек). Этот сервер используется для **Kubernetes liveness/readiness** проверок и должен быть максимально лёгким и быстрым.
    
    - Сервер должен:
        
        - слушать порт из переменной окружения `PORT` (по умолчанию `3000`), чтобы быть совместимым с Dyno/Kubernetes;
            
        - обрабатывать как минимум один маршрут `GET /healthz`.
            
    - Требования к `GET /healthz`:
        
        - Метод: `GET`
            
        - Путь: `/healthz`
            
        - Ответ: HTTP `200 OK`
            
        - Тело ответа — JSON:
            
            ```json
            {
              "status": "ok",
              "version": "<значение из SERVICE_VERSION>",
              "uptimeSeconds": <process.uptime()>,
              "timestamp": "<ISO8601>"
            }
            ```
            
        - Поле `version`:
            
            - брать из переменной окружения `SERVICE_VERSION`;
                
            - если переменная не задана — использовать значение по умолчанию `"0.0.1"`.
                
        - Поле `uptimeSeconds`:
            
            - значение `process.uptime()` (число секунд работы процесса).
                
        - Поле `timestamp`:
            
            - текущее время в формате `ISO8601` (`new Date().toISOString()`).
                
        - Заголовки ответа:
            
            - `Content-Type: application/json`
                
            - `Cache-Control: no-store`
                
    - Обработка других путей:
        
        - Любые другие пути, кроме `/healthz`, должны возвращать:
            
            - HTTP статус `404 Not Found`;
                
            - заголовок `Content-Type: text/plain; charset=utf-8`;
                
            - простое текстовое сообщение (например, `"Not Found"`).
                
    - Реализация должна быть:
        
        - без дополнительных middleware;
            
        - без лишной логики и тяжёлых операций внутри обработчика `healthz`;
            
        - отделена от бизнес-логики Moleculer (никакой тяжёлой проверки зависимостей; максимум — проверка состояния брокера, если это не вредит быстродействию).
            
    - При необходимости отдельного **readiness**-эндпоинта (`/readyz`) можно:
        
        - реализовать его в этом же HTTP-сервере;
            
        - использовать тот же подход с лёгким ответом JSON, но с дополнительными флагами готовности (например, `brokerConnected`, `adaptersReady`).
            

## 5. Инфраструктура и деплой

1. **Dockerfile**:
    
    - Базовый образ: `node:20-alpine`.
        
    - Multi-stage билд:
        
        1. Stage `builder`: установка зависимостей, сборка TypeScript.
            
        2. Stage `runner`: только production-зависимости и собранный `dist`.
            
    - Контейнер:
        
        - запускает Node.js-приложение (`node dist/index.js`);
            
        - использует `PORT` из окружения (для HTTP health-сервера / возможного API).
            
2. **docker-compose.yml**:
    
    - Один сервис, поднимающий контейнер микросервиса без внешних зависимостей.
        
    - Возможность запуска локально командой `docker-compose up --build`.
        
3. **.gitlab-ci.yml**:
    
    - Пайплайн с этапами:
        
        - `lint` — линтинг TypeScript-кода.
            
        - `build` — сборка.
            
        - `test` — базовые тесты (можно минимальные, но рабочие).
            
        - `build-image` — сборка Docker-образа.
            
4. **Переменные окружения**:
    
    - `.env.example` с примером ключевых переменных:
        
        - `PORT`
            
        - `NODE_ENV`
            
        - `METAL_API_MOCK` (true/false)
            
        - `PAYMENT_GATEWAY_MOCK` (true/false)
            
        - `SERVICE_VERSION` (версия сервиса для `/healthz`)
            
        - при необходимости — настройки логирования и уровня логов.
